# Независимое ревью Strangler через призму простоты и соглашений

Это самостоятельный анализ, вдохновленный обозначенной пользователем призмой DHH: простота модели, понятные
соглашения, целостность приложения и стоимость сопровождения. Это не мнение или одобрение DHH. Проверены текущие
файлы пакета, README, руководство адаптации и тесты; README и руководство содержат локальные изменения после
последнего коммита. Отчет другого агента не использовался. Код не изменялся, проверки качества повторно не
запускались.

**Вердикт:** идея оправданна для команды, которая уже поддерживает Yii 1.1 на PHP 8.2+ и хочет сохранить
существующий клиентский контракт. Для ограниченного внедрения архитектура понятна. До широкого внедрения следует
устранить небезопасное значение TLS по умолчанию, определить политику доверенных и клиентских заголовков, запрещать
отправку запросов с незаполненными идентификаторами и сделать процедуру подключения воспроизводимой. Сам пакет не
решает согласованность данных при откате.

Приоритеты: **P1** — существенный риск перед производственным внедрением; **P2** — заметная проблема контракта или
интеграции; **P3** — улучшение удобства или сопровождения. «Дефект» описывает существующее поведение, «риск
интеграции» зависит от приложения, «предложение» не означает поломку.

## Пять главных замечаний

1. **Безопасное значение TLS должно быть соглашением пакета, а не обязательным ручным исправлением.** Сейчас
   отсутствие ключа выключает проверку сертификата (`src/StranglerProxy.php:237`).
2. **Определить одну понятную политику trust boundary и headers.** Правильно полученный Yii user ID не отменяет
   необходимости защитить backend, отделить server-owned token от клиентского header и решить судьбу legacy
   Cookie/Authorization/Set-Cookie (`src/StranglerProxy.php:224`, `src/StranglerProxy.php:465`,
   `src/ResponseEmitter.php:43`). Это не утверждение, что любой deployment уязвим: инфраструктура может уже
   гарантировать необходимый канал.
3. **Не выполнять upstream write с исчезнувшим обязательным ID.** Молчаливый `/items/{id}` → `/items/` — изменение
   адресуемой операции, а не нормальный default (`src/StranglerProxy.php:430`, `tests/StranglerProxyTest.php:497`).
4. **Дать воспроизводимый путь от checkout до первого безопасного request.** Сейчас установка требует знания
   Composer path repositories, а защищенный hop не имеет примера. Нужны команды, фиксированная версия/ref, backend
   auth-конфигурация и простой тест запрета прямого вызова (`README.md:38`, `README.md:115`).
5. **Зафиксировать полный legacy-контракт ошибок.** Backend error и transport error имеют разные пути обработки;
   invalid JSON и ошибки адаптера ведут себя еще иначе. При отличающихся API именно это ломает клиента после
   успешного happy path (`src/StranglerProxy.php:270`, `src/StranglerProxy.php:176`, `src/ResponseEmitter.php:72`,
   `docs/api-adaptation.md:154`).

Не предлагается превращать библиотеку в платформу миграции, систему флагов или универсальный API gateway.
Предпочтительное направление — небольшой Yii-адаптер с безопасными defaults, явным контрактом перевода и короткой
инструкцией внедрения. Позитивная основа уже есть: поэтапная маршрутизация, понятный builder, сохранение
существующего клиента и отсутствие опасного автоматического повторения write-операций.
